# Which log line would have told me? A logging ablation on a three-agent LLM pipeline

Rakesh Reddy Karri. All numbers come from `results/` and are regenerated by `make report`.

## 1. Question

When an LLM pipeline gives a wrong answer, which log categories let you say **which step went wrong
first** and **which fault mechanism caused it**, and what does each category cost in size, write
time and sensitive content? The target is a minimum logging profile: the smallest set of categories
that keeps attribution within 5 points of full logging, checked on held-back runs.

## 2. Method

**Use case.** Incident triage for a simulated online shop (api-gateway, auth, catalog, checkout,
payment-db, cache; fixed dependency graph; six incident types, each with one root cause and one
correct action). A seeded generator plants synthetic e-mails, IPs, API keys and order ids and stores
the ground truth of every scenario.

**Pipeline** (F1). LangGraph: evidence agent -> handover 1 -> reasoning agent -> handover 2 ->
action agent, all qwen2.5:3b at temperature 0 through Ollama. Handovers are explicit graph nodes so
faults can be injected and state logged there. A deterministic outcome check (root cause, action
and target service must all match) is never traced.

**Faults** (F2). Eight faults, at most one per run, injected through hooks (agent code never
changes): E1 stale window, E2 wrong service, E3 missing alert, R1 misleading prior, R2 unstable
sampling, I1 dropped field, I2 truncated findings, I3 dropped target. P0 is a placebo (one routine
log line on a bystander service).

**Paired twins.** Every scenario first runs clean. Only scenarios whose clean run succeeded
(49 of 100) are faulted, and every faulted run stores its clean twin. With temperature 0 and a fixed
seed the twin is the counterfactual: a faulted run that fails while its twin succeeded is
*manifested* (the fault caused the failure), one that still succeeds is *masked*.

**Placebo.** The pilot showed that the pipeline is sensitive to cosmetic changes: changing only the
planted fake API-key prefix from `sk_live_` to `synth_key_` flipped 2 of 2 tested answers from right
to wrong (`results/pilot_summary.txt`). That is why a placebo control exists: the share of eligible
scenarios whose answer changes under a meaningless change (P0) is the baseline against which a
fault's manifestation rate is read.

**Dataset.** 375 runs: 100 clean (49 clean_success, 51 natural_failure), 245 faulted
(93 manifested, 152 masked), 30 placebo. cross_zone_latency has no eligible scenario (0 of 17 clean
runs succeeded), so it contributes no faulted runs. A manual diagnosis of two cross_zone runs
(`results/diagnostic_cross_zone.txt`) showed the evidence agent dropping the zone-change evidence
(the first error), after which the reasoning agent invented supporting detail; the raw tool results
did contain the decisive deploy record.

**Logging and ablation.** Everything is logged once; categories are removed afterwards by
filtering: C1 step_io, C2 tool_calls, C3 prompt_shown, C4 confidence, C5 timings, C6 handover_state,
plus a skeleton that is never removed. Conditions: full, minus each category, skeleton only,
skeleton plus one, and all 64 profiles. Every interval is a 95% paired cluster bootstrap over whole
scenarios (2,000 resamples).

**Split.** 70/30 by scenario, stratified by variant, committed before any rule was written
(71 design / 29 holdout scenarios). The profile was frozen and pushed before the holdout was read.

**Attribution.** A deterministic rule checker (one rule per fault, checked from the earliest step to
the latest, never reading labels) is the reference ceiling and the method used for all results. An
LLM judge (qwen2.5:7b, all-at-once over a fixed-budget rendering of the filtered trace) was built
and evaluated; see section 4.

## 3. Results

**Faults and placebo (F3).** A meaningless log line flips 20% of answers (6/30, CI 6.7-35.7%), so a
fault must be read against 20%, not against zero. Clearly above that baseline: R1 71% (22/31),
E2 63% (19/30), I2 61% (19/31), E3 43% (13/30). Not distinguishable from placebo: E1 26%,
I1 19%, R2 16%. I3 manifested once in 30 (3%), below the placebo rate: dropping suspected_service almost never
changed the final answer (not investigated further; the action agent may get the target from
elsewhere).

**What each category is worth (F4, F6; rule checker, design side, 66 manifested runs).** Full
logging attributes 92.4% of first errors and root causes. Removing C2 costs 37.9 points
(CI 21.5-53.8), removing C3 costs 15.2 (first error) and 18.2 (root cause, CI 10.5-27.0). Removing
C1, C4, C5 or C6 alone costs nothing measurable. C1 and C6 are substitutes for the interface
faults: alone each recovers 28.8%. The heatmap is clean: C2 is required for E1-E3 (100% recall
drop), C3 for R1 (85%), and the interface faults need C1 or C6. The remaining 7.6% of errors are
all caused by the E3 rule firing first on a run with another fault. Masked runs behave alike (full
91.7%, minus C2 -25.9, minus C3 -23.1): logs can reveal faults that did not change the answer.

**Cost (F5, T3).** Median bytes per run: C3 17.2 kB (36% of the total), C2 12.9 kB (26%),
C5 6.7 kB, C1 4.4 kB, C6 3.7 kB, C4 1.6 kB, skeleton 1.4 kB; full is 46.9 kB. Replaying the tracer's
write path costs 0.5 ms per run for everything on, 0.002% of the 29.5 s median run time.
Presidio finds 100% of IPs, API keys and order ids (precision 100%) but **0% of the planted
e-mails** (its validator rejects the `.test` domain), 77.6% of all planted values overall. About 46% of C3
events and 26% of C2 events contain a planted value.

**Lighter forms.** Masked C2 and C3 cost no accuracy and save few bytes (they only replace
values); with Presidio alone they still leak e-mails. C3-light (template id, sha256 of the system
prompt, options) keeps full accuracy at 975 bytes instead of 17,165.

**Minimum profile (F7, T4).** Over 320 candidates the smallest within 5 points is
**C2 masked (Presidio plus an extra .test e-mail pattern) + C3 light (template id,
system-prompt hash, options) + C6**, written `C2x+C3l+C6` in the figures and tables: 18.3 kB median
(39% of full, 3.9 kB gzip), 92.4% / 92.4% on the design side, 1.7 planted values per run instead
of 19.4.

**Holdout (F9, T5).** On 14 held-back scenarios the frozen profile scores 100% first-error and
100% root-cause on 27 manifested runs (full: 100%), and 97.7% / 97.7% on 44 masked runs (full:
97.7%); skeleton 0%. The profile passes the 5-point rule. The 100% intervals are degenerate
(no errors to resample); they are 27 runs from 14 scenarios.

## 4. The judge: a negative result

With the same taxonomy knowledge as the rule checker, the LLM judge did not learn to find the
faults. v1 predicted E2 for 10 of 10 runs (root cause 20%, rule checker 90% on the same runs). v2
(observations first, shuffled variant order, variant constrained to the chosen step) reached 12.5%
root-cause accuracy on a 16-run design-side dev set, v3 18.8% (first error 43.8%), against a chance
level of 12.5%; phi4-mini with v3 also 12.5%. The pre-set rule (one label above 60% or root cause
below 30%) marks it degenerate, so the full overnight judge run (about 6.5 h projected) was not started. The decisive evidence is a small
mismatch inside shortened JSON; a 7B model in about 3k tokens does not find it. Full log of versions
and scores: `results/judge_dev_log.md`.

## 5. Limitations

- **Synthetic data.** Scenarios are generated; real incident logs are noisier. Faults are clean and
  single.
- **Small model.** qwen2.5:3b at temperature 0 on one machine; other models fail in other ways.
  Roughly half of the clean runs already fail, which limits the faulted data.
- **Small samples.** 66 design and 27 holdout manifested runs; I3 has 1 manifested design run, R2 4.
  Per-variant recalls are directions, not sizes.
- **Circular rule checker.** The rules were written knowing the faults and the taxonomy, so its
  numbers are a ceiling on what each category *can* carry, not what an unaided analyst or model
  achieves. The E3 rule was narrowed on design-side data after the literal version fired on 46% of
  clean design runs.
- **Single split.** One 70/30 split (seed 42); the holdout confirmed the profile once, there is no
  repeated-split estimate.
- **Presidio and `.test` e-mails.** Stock Presidio misses every planted e-mail, so its entity counts
  understate exposure; the report uses planted ground truth for exposure and an added `.test` pattern
  for masking.
- **Single placebo position.** One placebo line at one place; a different bystander or line type
  could flip a different share.
- **Selection.** The profile is the smallest of many equally accurate candidates, chosen on 66 runs.
- **Dev set overlap.** The judge dev runs are part of the design side.

## 6. Future work

Apply the method to real operational logs in another domain, for example network fault
management, where the incident types and sensitive fields differ. Mask C6 as well (it still carries about 2 planted values per run; a post-hoc recommendation, not
applied). A larger or fine-tuned judge, or tool-assisted checking, on the same traces. More
incident types and real logs, repeated random splits, several placebo positions and lines, other
agent models and non-zero temperatures, and a precision-oriented E3 rule.
